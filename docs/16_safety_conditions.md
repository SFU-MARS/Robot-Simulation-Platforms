# 16 安全条件：量程、速度与计算延迟

2026-11-23。讨论稿：机器人在未知地图里边走边建图时，"不撞"除了要求 filter 正确，还要求 LiDAR 量程、最大速度和在线计算的延迟之间满足一定关系。这里把这些关系写下来，配上 Burger（Dubins 3D）和 QBot（Dubins 4D）的实际数字，再列出可以调的旋钮和要讨论的问题。第 16.5 节记录了 4D 拐角修正做到了哪里、为什么还太慢。

## 16.1 两种保证，靠的东西不同

| filter | 保证从哪来 | 需要满足 |
| --- | --- | --- |
| `backup`、`hj_backup` | 每个周期都找到一条"后路"（witness）：一段在已知空地里走完、最后安全停住（4D 刹停）或绕圈（3D）的轨迹；找不到就执行上一条已承诺的后路 | 条件 1 |
| 经典 `hj` | 并集 U = min_i V_i 在拐角处会漏，靠拐角修正（local update）把漏补上；没有后路兜底 | 条件 1 和条件 2 |

**未知区当障碍**（`unknown=occupied`，默认）：后路只能在已知空地里找，看不到的地方一律当障碍。**未知区当空地**（`unknown=free`）只在"障碍总是在车进入它的 BRT 之前被看到"时才安全，有遮挡（挡板后面藏着箱子）就做不到，所以默认不用。

## 16.2 条件 1：后路要有地方放

车朝未知区开时，已知空地的边（frontier）大约在 LiDAR 量程 R 处。后路要在撞上（按车半径膨胀后的）frontier 之前停下或躲开：

**R ≳ d_stop(v) + v·τ + r + c + ε**

| 符号 | 含义 | QBot | Burger |
| --- | --- | --- | --- |
| d_stop(v) | 刹车距离 v²/(2a)；3D 停不下来，换成绕圈需要的空间 | 0.64 m（0.8 m/s，0.5 m/s²） | 2 × 转弯半径 = 0.2 m |
| τ | 一个控制周期（加上扫描到控制的延迟） | 0.1 s → 0.08 m | 0.2 s → 0.02 m |
| r | 机器人半径 | 0.285 m | 0.124 m |
| c | clearance（1.5 个地图格子） | 0.06 m | 0.03 m |
| ε | 建图和面拟合的误差（约 1 个格子） | 0.04 m | 0.02 m |
| **合计** | | **约 1.1 m** | **约 0.36–0.4 m** |
| 现在的量程 R | 软件截断 | 2.0 m | 0.8 m |

- QBot 的 LiDAR 装在车头前 0.22 m，朝前开时还能多看一点。2.0 m 够用：批量里 MPPI 全速开，`backup` 几乎不介入，也不撞。
- Burger 已经验证过下限：遮挡场景量程 0.3 m 时，`unknown=occupied` 的车直接不出发（找不到后路），这是安全的失败方式；`unknown=free` 时撞了 8 次（[05](05_safety_filter.md)、README）。
- 转弯时 LiDAR 仍是 360°，所以这个条件不依赖朝向；但真机 LiDAR 有遮挡（车身支架）时要重新核对。

## 16.3 条件 2：拐角修正要来得及

只对经典 `hj` 必需。拐角在进入量程时被发现，它的修正要在车开进"并集会漏"的区域之前算好：

**(R − d_leak) / v ≥ T_wait + T_solve**，即 **R ≥ d_leak + v·(T_wait + T_solve)**

| 符号 | 含义 | QBot | Burger |
| --- | --- | --- | --- |
| d_leak | 拐角周围并集会漏的区域的半径 | 约 1.0 m（L 形凹角：漏都在拐角 0.65 个模型单位以内） | 约 0.2 m（L 形凹角、真实 V₀：一半的漏在拐角 0.12 m 以内，95% 在 0.19 m 以内；再远的部分受窗口边界影响，没测准） |
| v | 最大速度 | 0.8 m/s | 0.1 m/s |
| T_solve | 一个窗口的求解时间 | 0.6–1.2 s（numba，12 线程）；numpy 1–13 s | 约 0.4 s（numba，θ 30 格；[13](13_online_local_update.md) 的 0.09–0.13 s 是每个控制周期的平均，不是一个窗口） |
| T_wait | 排队：同时出现多个窗口时要等前面的算完 | 开局 5–7 个窗口一起出现，3–4 s | 小 |

代入 QBot 的数字：

- 只排一个窗口：R ≳ 1.0 + 0.8 × 1.0 = **1.8 m**，和现在的 2.0 m 几乎贴边；
- 开局 5 个窗口排队（约 3–4 s）：R ≳ 1.0 + 0.8 × 4 ≈ **4 m**。

Burger：R ≳ 0.2 + 0.1 m/s × 0.4 s ≈ 0.24 m，远小于 0.8 m 的量程，所以 3D 的拐角修正在线没问题（[13](13_online_local_update.md)）。

这也说明"在线"要求的不是每个控制周期（0.1 s）都算完，而是**车开到拐角之前修正已经算好**。车上能不能用，取决于 R、v、T_solve 三者是否配得上。

## 16.4 可以调的旋钮

| # | 旋钮 | 作用于 | 好处 | 代价 / 风险 |
| --- | --- | --- | --- | --- |
| 1 | **加大量程 R** | 条件 1、2 | 最直接：两个条件同时放宽 | 地图更大、面和窗口更多，T_wait 上升；硬件量程待确认（规格表只写了每秒 16,800 点） |
| 2 | **按离车的距离给窗口排队** | 条件 2（T_wait） | 最近的拐角先算；很便宜 | 远处的拐角更晚才有修正（车也更晚才到那里） |
| 3 | **按延迟限速** | 条件 2 | 修正没算好的拐角附近，速度压到 v ≤ (R − d_leak) / (T_wait + T_solve)，把条件变成 filter 的一条规则 | 到达时间变长；要有 T_solve 的可靠估计（车载电脑更慢） |
| 4 | **继续提速 T_solve** | 条件 2 | 所有条件都放宽 | 见 16.5：Gauss-Seidel 式更新（不再和 numpy 逐位相同）、更小的窗口 |

## 16.5 4D 拐角修正：做了什么，为什么还太慢

**方法**：拐角窗口里的稳态 local update（[13](13_online_local_update.md)）推广到 4D（`fast_brt.corner`）。数值格式和 HJ_local_update 里同事做的 4D local update（`value_change_numpy`，`dubins_4d`）逐位相同；在线不用逐时间步的版本，因为它要每个面每个时间步、和网格严格对齐的值。窗口按刹车距离定大小（3D 那套"半宽 = v·T + 1.5"搬到 4D 会大到算不动）：半宽 1.4 个模型单位（2.24 m），dx 8 cm，约 107 万个点。

**效果**（L 形凹角，真实 V₀，和同一窗口上推进到收敛的直接求解比）：并集漏了 493 个状态（全在 0.3–0.8 m/s），修正后剩 3 个，而且只差 0.0002–0.006；零水平集附近平均误差 0.003。

**速度**：

| 版本 | L 形凹角（2 个面） | 竞技场里最大的窗口（24 个面、37 对拐角） |
| --- | --- | --- |
| numpy | 1.1 s | 12.9 s |
| numba（可选依赖，12 线程，和 numpy 逐位相同） | — | 0.95 s |

做过的提速：U 的剪枝（远处不可能取到最小值的面不插值，`PrimitiveV0.min_value`，快 4 倍）；起始区域只在 x-y 平面上算；numba 把稳态更新和 U 编译成多线程（快 13.6 倍）。窗口的 θ、v 放粗只快不到一倍，误差变大，没采用。

**重算太频繁**：地图每个周期都在变，窗口不断作废。原来 60 个周期重算 185 次，触发原因：窗口里面的个数变了（面拆开或合并）72 次、frontier 移动 55 次、障碍面移动 49 次。改成 (1) 默认不修 frontier 拐角时 frontier 面不进窗口，(2) 只比较裁剪到窗口里的几何、容差 1.5 个格子以后，降到 89 次；剩下的触发是真的几何变化（中位数 9 cm、最大 62 cm），集中在开局探索阶段，之后平均每周期 0.3 次。

**闭环**（QBot，`hj` + pursuit，从 L 形凹角出发，`delayed` 模式如实算入求解时间）：numpy 版 17 次求解共 142 s；numba 版 26 次共约 28 s，到达，最近 4.7 cm。

**结论**：4D 拐角修正能用、能补上漏，但按 16.3 的条件 2，QBot 全速时 2.0 m 的量程只够一个窗口排队，开局多个窗口同时出现时不够。所以 `hj` 在 4D 默认不开拐角修正；需要安全保证时用 `hj_backup` 或 `backup`（批量里都没有碰撞，[15](15_qbot_dubins4d.md)）。

## 16.6 证书相同时，local update 有没有用

问题：在完全相同的后路证书下（同一个 backup filter 检查后路），加上 local update（拐角修正），能不能降低 backup 的拒绝和搜索代价、提高到达率、提高过窄通道的能力、让轨迹更有效率，而且不破坏 deadline？

**实验**（2026-11-24）：成对比较，同一张地图上起点、终点、随机种子完全相同，只改 local update。MPPI；Burger：`backup`、`hj_backup` × 关 / `delayed` / `sync` × hj、遮挡、4 档窄通道（每组 97 局）；QBot：`backup`、`hj_backup` × 关 / `delayed` × 竞技场、遮挡、4 档窄通道（每组 123 局）。窄通道是一堵墙中间一个缺口，起点在一侧、终点在另一侧（Burger 0.35 / 0.45 / 0.55 / 0.65 m，QBot 0.7 / 0.85 / 1.0 / 1.2 m）。`filter_batch.py --episodes-out` 记录每一局，`experiments/paired_compare.py` 逐局配对：到达率用精确符号检验（只看结果不同的局），连续指标用 Wilcoxon 符号秩检验。每步耗时不含拐角求解（在线时它在后台线程）。全部数字：[`figures/paired_local_update.md`](figures/paired_local_update.md)，逐局数据：[`figures/paired_local_update_episodes.csv`](figures/paired_local_update_episodes.csv)。

| 问题 | `backup` | `hj_backup` |
| --- | --- | --- |
| backup 拒绝率 | 不变（local update 只影响第一个候选） | **Burger 显著下降**：hj 场景 0.064 → 0.037（p < 0.001），遮挡 0.067 → 0.029（p = 0.03），窄通道 0.35 / 0.45 m 降 50–65%（p ≤ 0.03）；QBot 本来就约 0（刹停的后路几乎不拒绝） |
| 搜索代价 | HJ 候选成功的比例上升（Burger hj 0.69 → 0.78，窄通道最高 0.84 → 0.98；QBot 一直 1.00），但每步搜索时间多 2–6 ms（查拐角窗口） | 同左 |
| 到达率 | 所有地图逐局完全相同 | **没有提高**；Burger 遮挡 15 → 10（`delayed`，6 / 1 局不同，p = 0.12）、15 → 13（`sync`），窄通道 0.65 m 12 → 8（p = 0.12）；QBot ±1 |
| 窄通道 | 由证书决定：Burger 0.35、0.45 m 任何设置都过不去（绕圈要约 0.49 m），0.55、0.65 m 都过；QBot 0.85 m 以上都过，0.7 m 1 / 12 | QBot 0.85 m 只过 1 / 12（限制它的是 HJ 的 2 cm 余量，不是证书），开不开都一样；Burger 0.65 m 开了反而少 4 局 |
| 轨迹效率 | 路径和时间逐局完全相同 | Burger 窄通道 0.65 m 变差：到达时间 +2.6 s（`delayed`，p = 0.03）、+7.4 s（`sync`，p = 0.008）；其余无显著差别 |
| deadline（控制回路本身） | 变慢：每步 95 分位 Burger 遮挡 54 → 163 ms（0.5% 的周期超过 200 ms），QBot 遮挡 42 → 113 ms（**4.0%** 超过 100 ms） | QBot 遮挡 40 → 100 ms（0.8% 超过） |

不开 local update 时只有每批第一步超时（QBot 1–3 s 的一次性预热，可能是第一次查询时现算 V₀ 的梯度表，未核实），约 0.01%；实车上出发前预热一次即可。开了以后变慢，是因为每步都要查拐角窗口的值（`hj_margin`、`hj_control` 对每个子步、每个候选都查），大地图上窗口多。

**结论**：证书相同时，local update 让 HJ 的提议和证书更一致（`hj_backup` 的拒绝更少、后路更常是 HJ 候选给出的），但**没有提高到达率、窄通道能力或轨迹效率**，有的地图上还略差（修正后的值更保守，HJ 更早逃逸、更容易卡住）；大地图上还会拖慢控制回路。它的价值在于让经典 `hj` 更安全（16.5），而不是改善有证书保底的 `backup` / `hj_backup`。

**局限**：每格 12–40 局，到达率的差别单看都不显著（p ≥ 0.12），只是方向一致；只用了 MPPI 和一组随机种子；QBot 没有跑 `sync`；耗时在 12 线程的笔记本上测。

## 16.7 要讨论的问题

1. **车载电脑**：QBot 是 Jetson Orin Nano（6 核 Arm），这里的 0.6–1.2 s 是在 12 线程的笔记本上测的，车上的 T_solve 可能大好几倍。
2. **d_leak 有多普遍**：1.0 m 是一个 90° 凹角上量的。不同角度、不同速度上限下 d_leak 会变，需要扫一遍。
3. **限速（旋钮 3）放在哪一层**：是 filter 的一条规则（修正没算好时限速），还是交给 nominal（MPPI 的速度代价）？前者能给出保证，后者只是倾向。
4. **经典 `hj` 还要不要在 4D 上追求不撞**：如果车上用的是 `hj_backup`，拐角修正只影响 HJ 介入得准不准，不影响安全；那么 4D 拐角修正的优先级可以降低。
5. **frontier 拐角**：3D 批量里修不修安全上没有差别（[13](13_online_local_update.md)），默认不修；量程更短、遮挡更多时可能需要，要在那种场景里再比一次。

**批量**（2026-11-23，重算规则改了以后，`delayed`，numba；原始数据 [`figures/batch_corners_reuse.csv`](figures/batch_corners_reuse.csv)、[`figures/batch_qbot_corners.csv`](figures/batch_qbot_corners.csv)），到达 / 碰撞 / 超时：

| 机器人、场景 | filter / nominal | 改前（或不修正） | 改后 | 窗口求解次数 |
| --- | --- | --- | --- | --- |
| Burger hj（26 次） | `hj` / MPPI | 22 / 2 / 2 | 23 / **3** / 0 | 1463 → 318 |
| Burger 遮挡（23 次） | `hj` / MPPI | 20 / 0 / 3 | 22 / 0 / 1 | 2104 → 953 |
| Burger hj | `hj_backup` / MPPI | 15 / 0 / 11 | 15 / 0 / 11 | 1740 → 470 |
| Burger 遮挡 | `hj_backup` / MPPI | 12 / 0 / 11 | 14 / 0 / 9 | 2750 → 1258 |
| QBot 竞技场（40 次） | `hj` / pursuit | 不修正 28 / 2 / 10 | 27 / 2 / 11 | 613，每步 112 ms |
| | `hj` / MPPI | 不修正 34 / 0 / 6 | 33 / 0 / 7 | 746，每步 153 ms |
| QBot 遮挡（35 次） | `hj` / pursuit | 不修正 14 / 2 / 19 | 14 / 1 / 20 | 813，每步 86 ms |
| | `hj` / MPPI | 不修正 32 / 0 / 3 | 32 / 0 / 3 | 1328，每步 238 ms |

- **3D**：重算少了 2–4.6 倍，到达数持平或更多，`hj_backup` 仍然 0 碰撞；`hj` 在 hj 场景多撞 1 次（2 → 3）。这次同时变了两样：复用规则放宽了，numba 让求解变快（`delayed` 如实算入求解时间，修正生效的时机也变了），所以这一次不能全算在新规则上；这类碰撞之前诊断过，只漏 5–12 mm，正好在复用容差附近。
- **4D**：拐角修正几乎没有改善 `hj` 的安全（碰撞 4 → 3）。这和条件 2 的推论一致：拐角计算每步平均 86–238 ms，多数超过 100 ms 的控制周期，修正常常来不及。也可能这几次碰撞不是拐角漏；4D 还没有像 3D 的 `hj_failures.py` 那样的诊断，分不开。
6. **local update 在有证书的系统里还值不值得开**：16.6 的结果是拒绝更少，但到达率、窄通道、效率都没有改善，控制回路还变慢。如果车上用 `hj_backup` / `backup`，是否默认关掉 local update，只在经典 `hj` 上用？窗口查询能不能更便宜（只查覆盖当前状态的窗口、缓存）？
