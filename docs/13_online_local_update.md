# 13 在线修 leaking corner：稳态 local update

> 日期：2026-11-22 / 23。状态：**已接进 Robot-Sim**（`SceneFilter(corners=True)`，sync / delayed / thread 三种模式）；`hj` 的拐角碰撞在批量里消失；ROS 实跑和默认值待定。
> 代码：fast-brt `fast_brt/corner.py`（`robot-sim` 分支）。动力学：恒速 Dubins 3D，模型单位（v = ω_max = 1，R = 1）。

## 13.0 名词

| 名词 | 意思 |
| --- | --- |
| R | 转弯半径 v / ω_max；Burger 是 0.1 m。V₀ 在 v = ω_max = 1 的模型单位下求解，这时 R = 1，文中长度都用 R，乘 0.1 m 就是 Burger 上的距离（0.01 R = 1 mm） |
| θ | 车头朝向，状态 (x, y, θ) 的第三维。"θ 30 / 60"是拐角窗口网格在 θ 方向的点数（每 12° / 6° 一个点），V₀ 自己用 60 |
| 一阶步进 | HJ 方程在网格上推进一个时间步：用相邻格点的差算左右导数（一阶 ENO），按导数符号选最优控制，加 Lax-Friedrichs 耗散，前向 Euler：`V_新 = V + dt·(H + 耗散)`。一阶 = 只用最近的邻居，对应 odp 的 `accuracy="low"`，和 local update、low 的 V₀ 同一格式 |
| 向量化 | 一次对成千上万个格点做 numpy 数组运算，而不是 Python 循环逐点算（HJ_local_update 的 numpy 版每点 14 µs，向量化后约 0.05 µs），结果逐位相同 |
| frontier | `unknown="occupied"` 时，已知空地和未知区域之间的边界线；上面也放了 primitive（导读里橙色的那几段） |
| frontier 参与的拐角 | 相交的两个面里至少有一个是 frontier 边（例如一面墙和未知区域的边界相接）。修它能保证 `hj` 不会从拐角钻进还没看过的地方；代价是 frontier 每次扫描都往外推，这类窗口几乎每个周期都要重算（重算次数约多 60%） |

## 13.1 结论

1. **计划改了**：不照搬 HJ_local_update 的"逐时间步 local update"，改成**稳态 local update**：在拐角附近的小窗口里，从并集 `U = min_i V_i` 出发，反复做一步 BRT 算子 `V ← min(ℓ, V + dt·H(V))`，只更新值还在变的点和它们的邻居，直到收敛。**只需要 V₀ 的最后一层**，不需要时间历史，任意拐角角度都能用。
2. 直接求解（窗口里所有点、推进固定时间）保留成**参考解**，用来验证稳态 local update 的精度、比较耗时。
3. 前提是**单个 primitive 的 BRT 在 V₀ 的 horizon（T = 2）已经收敛**（已验证，见 13.3）。修正后得到的是**收敛后（无限 horizon）的联合 BRT**：单个面和 T = 2 没有区别；凹角处会比 T = 2 的联合 BRT 更大（更保守），这才符合"永远不撞"。
4. 共用的核 —— 向量化的一阶步进 —— 已经写好，和 HJ_local_update 的 `value_change_numpy`（也就是 odp `low`）**逐位相同**。
5. 风险：在线的 U 是插值出来的，不是窗口格式的严格不动点（13.5）。**不影响安全**（迭代只会让值变小），但可能增加计算量，需要实测。

## 13.2 为什么改：HJ_local_update 需要整段时间历史

HJ_local_update 的 local update（`numpy_impl/growing_region.py`）是**逐时间步推进**的：第 i 步在泄漏区域里，用第 i−1 步已修正的值重算一步；区域外直接用"并集在第 i 步的值"。所以它需要每个面在**每一个时间步**、在**同一张网格上**的值。和 BRS / BRT 无关，这是算法本身的结构。

在线用它有三个问题：

| 问题 | 说明 |
| --- | --- |
| 时间历史太大 | 241 网格、T = 2 约 125 步，一个 V₀ 的全部时间层约 1.75 GB（现在只导出了最后一层，14 MB） |
| 必须和网格严格一致 | local update 用"和并集的值不一样"判断哪里要修。任意角度的面要插值旋转，插值误差会被当成"要修"，区域一路扩散。只有 90° 倍数、整格平移的面严格一致 |
| 速度 | numpy 版是逐点的 Python 循环，每点 14 µs；一个拐角的泄漏集合几千到几万个点 × 125 步 = 9–90 s。而且它在文件顶部 `import heterocl`，没有 HeteroCL 的机器（笔记本、机器人）导入不了 |

### BRT 不是各时刻 BRS 的并集（避障时）

课件上 `V_BRT = min_u min_t ℓ(x(t)) = min_t V_BRS(t)` 说的是 **reach**（控制想到达，两个 min 可以交换）。避障是 `max_u`：

```
V_BRT = max_u min_t ℓ(x(t))  ≤  min_t max_u ℓ(x(t)) = min_t V_BRS(t)
```

量词顺序是 `∀u ∃t`（不论怎么控制，某个时刻会撞）对 `∃t ∀u`（存在一个固定时刻，不论怎么控制都在障碍里）。例子：厚 ε 的墙，车头正对着、离墙 h（0 < h < 1 R）。直行的轨迹只在 t ∈ [h, h + ε] 在墙里，打死方向的轨迹要到 t = arcsin h > h 才碰到墙线；ε < arcsin h − h 时没有共同的时刻，这个状态不在任何一个 BRS 里，但在 BRT 里（详细见 [12](12_local_update_brt.md)）。所以修正要用带 `min(ℓ, ·)` 的 BRT 算子，不能从各时刻 BRS 拼。

## 13.3 证据：单个面收敛，拐角要更久

旧 FaST-BRT 的 numpy 一阶求解器，101–121 网格，线性编码，α = 20：

| 情况 | T | 和 T = 6（或 8）比：零水平集附近最大差 | 符号不同的点 |
| --- | --- | --- | --- |
| 单个面 L = 1 R | 1.5 / 2 | 0.019 / **0.0004** | 0 / **0** |
| 单个面 L = 4 R | 1.5 / 2 | 0.083 / **0.003** | 0.038% / **0** |
| L 形凹角（两条 6 R 的面） | 2 / 3 / 4 | 0.77 / 0.048 / 0.0006 | 0.26% / 0.006% / 0 |

单个面在 T = 2 已经收敛（和精确解"horizon ≥ π/2 即可"一致）；凹角要到 T ≈ 4，因为从凹角里逃出来要掉头。

## 13.4 稳态 local update

记一步 BRT 算子 `F(V) = min(ℓ, V + dt·H(V))`（一阶 ENO、Lax-Friedrichs、前向 Euler，和 odp `low` 一样），ℓ = min_i ℓ_i。

- 每个 primitive 收敛：`V_i = F_i(V_i)`（F_i 用 ℓ_i）；
- F 是单调的（CFL 条件下），而 `U ≤ V_i`、`ℓ ≤ ℓ_i`，所以 `F(U) ≤ F_i(V_i) = V_i` 对每个 i 成立，`F(U) ≤ U`；
- 于是从 U 出发 `V ← F(V)` **单调下降**，收敛到 ≤ U 的最大不动点，也就是所有面合在一起的（收敛）BRT；
- U 已经是不动点的地方不会变，只需要在值还在变的点和它们的邻居上计算。

原型（L 形凹角，101² × 48 网格，同一个求解器算的 V_i）：

| | 结果 |
| --- | --- |
| 并集比联合 BRT 偏不安全的点（leaking corner） | 2893 个（0.59%） |
| 稳态 local update | 324 轮收敛；和联合 BRT（T = 8）零水平集附近最大差 0.0001 |
| 点更新次数 | 2050 万，直接求解（T = 8）2.46 亿，**少 12 倍** |

## 13.5 风险：插值出来的 U 不是严格的不动点

上面的推理要求 U 在窗口网格上是 F 的不动点。在线的 U 是用 V₀ 点查询插值到窗口上的。用真实 V₀（线性 / low）测残差 `U − F(U)`：

| 情况 | 99% 分位 | 最大 |
| --- | --- | --- |
| 单个面（本该为 0，纯插值误差），dx = 0.05 | 0.022–0.028 | 0.054 |
| 单个面，dx = 0.1 | 0.026–0.029 | 0.081 |
| 凹角附近（真正的泄漏） | 0.038–0.043 | 0.13–0.20 |

插值误差主要在障碍边界上（V₀ 在那里有折角，线性插值偏高），和真正的泄漏同一量级，单靠阈值分不开。

- **安全**：不受影响。迭代只让值变小，结果永远 ≤ U，不会比现在的并集更危险；插值误差带来的额外下调最多约 0.05（距离约 0.01 R = 1 mm），偏保守。
- **计算量**：修正可能沿窗口里所有面的边界扩散，最坏接近整个窗口（和直接求解同一量级）。
- **应对**：初始区域按几何选（拐角附近两个面的切换面，即 HJ_local_update 的 leaking set），扩散时用阈值挡掉很小的变化；实测点数和耗时。

## 13.6 实验：L 形凹角，真实 V₀

两条 3 R 的面在原点相接（自由空间在第一象限），V₀ = 线性 / low。窗口以 (1, 1) 为中心、半宽 3.5 R，60 个 θ；参考解是同一窗口、同一步进直接求解到 T = 4（凹角在 T ≈ 4 收敛）；只统计窗口内圈（离边缘 > 1.2 R）、障碍外的状态。脚本在 scratchpad（`corner_exp.py`、`corner_cross.py`），结论如下。

**和同一 dx 的参考解比**（偏不安全 = 结果说安全、参考解说在 BRT 里）：

| dx | 方法 | 偏不安全的点 | 零水平集附近最大差 | 点更新 | 耗时 |
| --- | --- | --- | --- | --- | --- |
| 0.1 | 并集 U | **1852** | 5.19 | — | — |
| 0.1 | 稳态，阈值 1e-3 | 0–2 | 0.02 | 5 M | 0.2 s |
| 0.1 | **稳态，阈值 1e-4** | **0** | 0.002 | 8 M | **0.3 s** |
| 0.1 | 稳态，阈值 1e-2 | 约 500 | 0.19–0.29 | 2.4 M | 0.1 s |
| 0.1 | 直接求解 T = 4 | — | — | 45 M | 1.4 s |
| 0.05 | 并集 U | **8261** | 5.5 | — | — |
| 0.05 | 稳态，阈值 1e-3 | 332–369 | 0.03 | 21 M | 1.0 s |
| 0.05 | **稳态，阈值 1e-4** | **44** | 0.003 | 32 M | **1.4 s** |
| 0.05 | 直接求解 T = 4 | — | — | 296 M | 9.5 s |

**和更准的 dx = 0.05 参考解比**（在线用法：`min(U, 窗口值)`，窗口值插值到细网格上）：

| 方法 | 偏不安全的点 | 最差的差（换成距离） |
| --- | --- | --- |
| 并集 U | 8261 | 0.985 R（约 10 cm） |
| 稳态，dx = 0.1 | 826 | **0.024 R**（2.4 mm） |
| 稳态，dx = 0.05 | 44 | 约 0.001 R |

- 稳态 local update 把凹角的泄漏从约 10 cm 压到毫米级；点更新比直接求解少 6–9 倍。
- 插值风险在实际中不严重：用残差做起点（含插值误差）和用几何起点，点数和精度几乎一样，修正没有扩散到整个窗口。
- 阈值要随 dt 变小：1e-4 在两种 dx 下都够；1e-2 太粗。
- dx = 0.1 剩下的 2.4 mm 是窗口网格本身的分辨率误差，小于 3 cm 的 clearance。在线默认 dx = 0.1（每个拐角 0.3 s），dx 做成可调。

## 13.7 接进 Robot-Sim：拐角窗口

代码：fast-brt `fast_brt/corner.py` 的 `find_corners`、`corner_windows`、`solve_window`、`CornerWindow`；Robot-Sim `nav_core/safety/scene.py`（`SceneFilter(corners=True, ...)`）。

- **找拐角**：放好的面（含 frontier 边）两两比较，自由侧的那条边相距不到 0.3 R 就算一个拐角；相近的拐角共用一个窗口（半宽 reach + 1.5 R，可用部分再往里缩 1.2 R）。
- **修正**：窗口内 U = 这些面从 V₀ 查出来的值取 min，ℓ = 它们的矩形取 min；从拐角附近、两个面的切换带（HJ_local_update 的 leaking set）出发做稳态更新。
- **只修自由侧**：矩形内部（ℓ ≤ 0）固定不动，相当于把面前、面后隔开。凸角障碍的两个薄矩形背面会围出一个"凹口"，那里在真实世界里是障碍内部，不需要修。
- **永不调高**：每次更新取 `min(旧值, 新值)`。理论上 U 已经满足 F(U) ≤ U，但插值出来的 U、或者没完全收敛的单面值，个别点会 F(U) > U，调高是不安全的方向。加上以后凹角、60° 拐角的精度和速度都更好（下表）。
- **使用**：`Scene.value`、`hj_margin`、`hj_control` 在窗口可用部分内取 `min(并集, 修正值)`；修正值更低的地方，u* 用窗口的 ∂V/∂θ。三种 filter 都受益（backup 的 HJ 候选、hj、hj_backup）。
- **只修机器人附近的拐角**（离机器人不超过 reach + 窗口半宽），**按容差复用**（窗口中心和每条面的端点都在 `corner_reuse` = 0.2 R = 2 cm 以内就用旧解，小于 clearance），**热启动**（几何变了时从 `min(U, 上一个窗口的解)` 开始；地图只会累积，旧解只会偏保守）。

自由侧精度（和 dx = 0.05 直接求解比，最差的差换成距离）：

| 拐角 | 并集 | 修正，θ 60 | 修正，θ 30 | 每个窗口（θ 60 / 30） |
| --- | --- | --- | --- | --- |
| 凹角 L | 0.985 R | 0.009 R | 0.044 R | 0.59 s / 0.34 s |
| 凸角 | 0.148 R | 0.009 R | 0.035 R | 0.59 s / 0.36 s |
| 60° 凹角 | 1.156 R | 0.011 R | 0.028 R | 0.52 s / 0.29 s |

**真正危险的是凹角**（并集漏约 1 R），凸角只漏 0.15 R。

闭环（hj_reach_target 第 10 次 run，MPPI + `hj`，原来撞在西墙和 obstacle 1 之间的凹角）：开启修正后**安全到达**，最小距离 1.5 cm。开销（207 个周期）：

| 设置 | 窗口重算 | 总耗时 | 每个周期平均 |
| --- | --- | --- | --- |
| 全部拐角，θ 60，冷启动 | 256 | 182 s | 0.88 s |
| 全部拐角，θ 60，热启动 | 256（216 次热启动） | 105 s | 0.51 s |
| 全部拐角，θ 30，热启动 | 264 | 56 s | 0.27 s |
| 只修障碍面之间的拐角 + 容差 5 cm + θ 30 + 热启动 | 58 | 15 s | 0.075 s |

重算频繁是因为地图每个周期都在变，尤其 frontier 每次扫描都往前推。每次重算要几百轮迭代把变化传开，每轮约 1.4 ms，已经接近 numpy 向量化的极限。在线（每周期 0.2 s）需要**异步**计算：算好之前用上一份窗口（或只用并集），由 backup 兜底。

### 批量（MPPI + `hj`，unknown occupied，拐角修正 θ 30，机器人半径 0.105 m，2026-11-23）

`experiments/filter_batch.py --filters hj --worlds hj occluded --corners --corner-theta 30`（当时还修 frontier 拐角）。到达 / 碰撞 / 超时（半径改成 0.124 m 以后的数字见本节最后）：

| 场景 | 不修正 | 修正 | 最小距离 | 拐角修正开销 |
| --- | --- | --- | --- | --- |
| hj_reach_target（27 次） | 20 / **7** / 0 | **25 / 0** / 2 | 1.2 cm | 每步 192 ms（3684 次窗口重算） |
| 遮挡（23 次） | 19 / **4** / 0 | 19 / **2** / 2 | −0.1 cm | 每步 516 ms（8973 次） |

- hj 场景的碰撞全部消失；到达数从 20 增加到 25，比 `backup` 的 16 还多：`hj` 不要求 loiter circle，那条 0.4 m 的窄缝能进去。
- 遮挡场景还剩 2 次碰撞，**都不是 leaking corner**（`hj_failures.py --worlds occluded --corners --corner-theta 30 --verbose`）：
  - 第 13 次：U 在一个周期里从 +0.24 跳到 −0.56，最近的面换成一个新出现的面，它单独就已经逃不掉：障碍出现时机器人已经在它的 BRT 里（遮挡场景设计的"挡板后的箱子"）；
  - 第 16 次：机器人在 U ≈ −1.3 的区域里待了很久，那段时间真实世界里其实还能逃（修正后的值在这里偏保守，可能来自当成障碍的 frontier）；经典 `hj` 进了 U < 0 只会按 u* 硬拐，躲 1 号面时撞上了 9、10 号面；
  - 这两点是经典 `hj` filter 本身的局限（对突然出现的障碍没有提前量、进入 BRT 后没有安全的恢复），正是 `hj_backup` 用 backup 兜底的理由。
- 开销太大：同步计算时每步 0.2–0.5 s，比控制周期还长。重算次数多是因为地图（尤其 frontier）每个周期都在变。

### 异步（2026-11-23，用户确认做异步）

`SceneFilter(corners=True, corner_mode=...)`：每个拐角一个"槽"，存着最近一份解好的窗口和最多一个正在算的任务。每个周期：先把算完的任务收进槽；窗口的面相对槽里那份移动超过 `corner_reuse` 且没有任务在算时，提交一个新任务（用旧解热启动）；这个周期先用槽里已有的解（可能过时），没有就只用并集。

| `corner_mode` | 用途 | 什么时候能用上新解 |
| --- | --- | --- |
| `sync` | 对照 | 当场算、当场用 |
| `delayed` | **仿真**（可复现） | 当场算出来，但要等仿真时间过了实测计算时间才用；任务在一个模拟的后台线程上排队 |
| `thread` | **在线 / ROS** | 后台线程算完以后 |

在用上新解之前，`hj` 可能比同步版多漏一点（过时的窗口不包括刚长出来的那部分拐角）；`hj_backup` 和 `backup` 的安全仍然由 backup 保证。

### 异步 + frontier 拐角修不修（机器人半径 0.105 m，2026-11-23）

`filter_batch.py --filters hj hj_backup --worlds hj occluded --corners --corner-mode delayed [--corner-frontier]`，θ 30，MPPI，unknown occupied。到达 / 碰撞 / 超时，括号里是介入率；最后一列是拐角计算每步的平均耗时：

| 场景 | filter | 不修正 | 同步，含 frontier | delayed，含 frontier | **delayed，只修障碍面之间** |
| --- | --- | --- | --- | --- | --- |
| hj（27 次） | `hj` | 20 / **7** / 0 | 25 / 0 / 2，192 ms | 25 / 0 / 2，117 ms | **25 / 0 / 2，90 ms** |
| 遮挡（23 次） | `hj` | 19 / **4** / 0 | 19 / 2 / 2，516 ms | 20 / 1 / 2，192 ms | **21 / 1 / 1，131 ms** |
| hj（27 次） | `hj_backup` | 16 / 0 / 11（0.29） | — | 16 / 0 / 11（0.41），70 ms | **16 / 0 / 11（0.42），55 ms** |
| 遮挡（23 次） | `hj_backup` | 14 / 0 / 9（0.37） | — | 13 / 0 / 10（0.41），125 ms | **13 / 0 / 10（0.40），85 ms** |

- **frontier 拐角修不修，安全上没有差别**（碰撞次数完全一样），不修省 23–32% 的计算，到达数一样或多 1 次。**默认改为只修障碍面之间的拐角**（`corner_frontier=False`），修 frontier 拐角保留成选项，以后在量程更短、遮挡更多的场景再比。
- **delayed（如实算入延迟）和同步一样安全**。delayed 的重算次数少得多（1582 对 3684）：算好之前沿用旧窗口，几何在这期间又变了的拐角只算最后一次。拐角计算每步约 0.09–0.13 s：在线用一个后台线程大约占一半时间，可行。
- `hj_backup` 加上拐角修正后安全和到达不变（本来就 0 碰撞），HJ 介入变多（0.29 → 0.41）：拐角处的值更准、更保守，HJ 更早避让。
- 剩下的 1 次 `hj` 碰撞和之前诊断的一样，是经典 `hj` 的局限，不是拐角漏。

### 机器人半径改成 0.124 m 后重跑（2026-11-23）

Burger 的位姿在轮轴中心，底盘后角离轴心 0.1237 m，`footprint_radius` 从 0.105 改成 0.124（包住整台车的圆）。所有批量重跑，原始数据 [`figures/batch_hj_corners.csv`](figures/batch_hj_corners.csv)（sync）、[`figures/batch_corners_delayed.csv`](figures/batch_corners_delayed.csv)（delayed）。hj 场景有一个起点离墙太近被筛掉，剩 26 次。MPPI，unknown occupied，θ 30，到达 / 碰撞 / 超时（介入率），最后是拐角计算每步的平均耗时：

| 场景 | filter | 不修正 | sync，只修障碍面之间 | delayed，含 frontier | **delayed，只修障碍面之间** |
| --- | --- | --- | --- | --- | --- |
| hj（26 次） | `hj` | 19 / **7** / 0 | 22 / **2** / 2，139 ms | 22 / **2** / 2，123 ms | **22 / 2 / 2，90 ms** |
| 遮挡（23 次） | `hj` | 22 / **1** / 0 | 20 / 0 / 3，228 ms | 19 / 0 / 4，189 ms | **20 / 0 / 3，118 ms** |
| hj（26 次） | `hj_backup` | 15 / 0 / 11（0.34） | — | 15 / 0 / 11（0.43），74 ms | **15 / 0 / 11（0.43），55 ms** |
| 遮挡（23 次） | `hj_backup` | 15 / 0 / 8（0.34） | — | 9 / 0 / 14（0.41），141 ms | **12 / 0 / 11（0.41），77 ms** |

- **`hj_backup` 仍然在所有设置下 0 碰撞**；frontier 拐角不修仍然更省、到达更多，默认不变。
- **`hj` 加修正后 hj 场景又有 2 次碰撞**（半径 0.105 时是 0）。`hj_failures.py --worlds hj --corners --corner-theta 30 --verbose` 把两次都判为 leaking corner，但漏得很少：进入真实 BRT 的那个周期，修正后的 U 只有 +0.121 和 +0.052（模型单位，即 5–12 mm），下一个周期就变成负的，经典 `hj` 再躲已经来不及。这个量级和拐角窗口的网格（1 cm）、建图栅格（2 cm）同级；半径变大后通道更窄，贴着拐角走的情况更多，原来的 0 次是踩着边过的。
- **加 margin 不是免费的**（`filter_batch.py --filters hj --worlds hj pillar occluded --corners --corner-mode delayed --margin 0.02`）：hj 场景 24 / 0 / 2，柱子 26 / 0 / 2，遮挡 12 / **1** / 10。margin 让 `hj` 更早进入逃逸模式（介入率 0.41–0.46），在遮挡场景的拐角附近被困住、超时变多，还多了 1 次碰撞（margin 1 cm 时 hj 场景不撞了，遮挡场景撞 2 次）。所以 `hj` 的默认 margin 仍是 0：经典 `hj` 对这种毫米级的数值误差没有余量，也没有安全的恢复，这正是 `hj_backup` 用 backup 兜底的理由。

### 重算规则（2026-11-23）

默认不修 frontier 拐角时，frontier 面不再进窗口（求解和复用检查都不看它们，它们仍在并集里）；复用检查改成比较裁剪到窗口里的几何（Hausdorff 距离），容差默认 1.5 个地图格子（Burger 3 cm）。3D 的窗口求解次数少了 2–4.6 倍；批量结果和讨论见 [16](16_safety_conditions.md) §16.5。

## 13.9 决策记录

- 2026-11-23：拐角窗口的 θ 默认 30 个点（仿真先用 30：最差误差约 4 mm，在 clearance 以内，比 60 快一倍）；`corner_theta=None` 用 V₀ 的 60。frontier 参与的拐角修不修，见下一条。
- 2026-11-23：`hj` 默认开拐角修正（它的安全全靠这个），`hj_backup` 默认不开（安全不变，只会更多介入）；ROS 节点默认 `corner_mode="thread"`。
- 2026-11-23：Burger 半径改成 0.124 m 后，`hj` + 拐角修正在 hj 场景有 2 次碰撞（修正后的值只漏 5–12 mm）。试过 margin 1 / 2 cm：hj 场景不撞了，但遮挡场景超时和碰撞变多，所以 `hj` 的默认 margin 保持 0，把它记成经典 `hj` 的局限；要安全保证用 `hj_backup`。
- 2026-11-23：在线速度用异步（`corner_mode`：sync / delayed / thread）。
- 2026-11-23：frontier 拐角修与不修的对比显示安全无差别、不修省 23–32% 计算，默认只修障碍面之间的拐角（用户本来就觉得每次扫描都重算代价太高）。
